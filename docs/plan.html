Implementation plan

t3-import: trazer threads de Claude, Codex, Grok e OpenCode para o T3 Code

novo repo t3code-import (Rust) · 2026-10-08 · v3 (revisado por gpt-6.1-sol)

Um binário Rust portátil que lista todas as sessões locais dos CLIs de agente, deixa a pessoa escolher quais quer e grava essas threads no banco do T3 Code, com histórico completo e retomáveis pelo provider original.

Context

  • O T3 Code já tem um importador (apps/server/src/project/AgentSessionScanner.ts + AgentSessionImporter.ts, RPCs agentSessionsScan/agentSessionsImport), mas: só Claude e Codex; importa todas as threads recentes de uma pasta de uma vez (sem escolha); janela de 30 dias; máx. 100 transcripts por import e 200 mensagens por thread (constantes fixas no servidor, linhas 62–96).
  • Quem migra trabalho para o T3 quer o histórico inteiro — senão começa do zero. Limites não são aceitáveis.
  • Patch upstream está descartado. Decisão: gravar direto no statev2.sqlite com o T3 fechado, protegido por validação de schema que trava e manda a pessoa abrir issue no GitHub se algo divergir.

Como o T3 guarda uma thread importada (orchestration-v2)

  • Log de eventos unificado: tabela orchestration_events, linhas com application_event_version = 2, aggregate_kind = 'thread', stream_id = threadId.
  • O importador nativo emite 4 tipos: thread.created → (message.updated + turn-item.updated) por mensagem → provider-thread.updated. Id determinístico import:<providerInstanceId>:<sessionId>, historyOrigin: "v1_import".
  • O EventSink grava evento + projeção + orchestration_v2_projection_metadata.last_sequence na mesma transação. Tabelas afetadas: projection_threads, projection_messages, projection_turn_items, turn_item_positions, projection_provider_threads; mais um upsert em provider_session_runtime (resumeCursor).
  • Não há rebuild automático no boot. ProjectionMaintenance.verify/rebuild existe mas só é chamado em testes. Logo, o app precisa escrever eventos e projeções, coerentes, e avançar last_sequence.
  • O resume é genérico: o orchestrator retoma pelo providerThread.nativeThreadRef.nativeId — Claude --resume, Codex thread id, Grok via ACP session/load, OpenCode sessionID. Estender para Grok/OpenCode é só escrever o leitor de transcript.
  • Projetos: t3 project add <path> já funciona offline (escreve via ProjectService quando não há servidor vivo). Usamos o caminho oficial, sem replicar eventos de projeto.

Approach

Rust, binário único por plataforma (macOS arm64/x64, Linux x64/arm64 musl, Windows x64), rusqlite com SQLite embutido, TUI em ratatui. O app tem três camadas: scanners (um por CLI, saída normalizada), picker (TUI) e writer (guarda de schema + transação SQLite que replica exatamente o que o importador nativo faria, sem limites).

A regra de ouro do writer: só escrevemos formatos que validamos. Antes de qualquer escrita, calculamos um fingerprint do banco e comparamos com fingerprints conhecidos; diferença = trava com mensagem e link pré-preenchido de issue. Rejeitado: escrever só eventos e esperar rebuild (não existe no boot); RPC nativa (limites fixos); patch upstream (decisão do Paulo).

Steps

1. Esqueleto + modelo normalizado

  • Crate t3-import (bin) com módulos scan/, t3db/, tui/.
  • Tipo comum SessionSummary { provider, session_id, cwd, title, created_at, updated_at, message_count, source_path } e Transcript { messages: Vec<Msg { role, text, created_at }>, model } (carregado sob demanda).
  • CLI não-interativa também: t3-import list --json, t3-import import <ids…> — facilita teste e automação.

2. Scanners (sem limites)

  • Claude: ~/.claude/projects/*/*.jsonl (respeitar CLAUDE_CONFIG_DIR). Portar as regras de parsing do AgentSessionScanner.ts (filtra sidechain/meta, extrai texto de blocos, cwd do record, título do summary ou primeira msg). Só ids UUID são retomáveis (mesma regra do nativo).
  • Codex: ~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl + archived_sessions (respeitar CODEX_HOME); session_meta dá id e cwd.
  • Grok: ~/.grok/sessions/<cwd url-encoded>/ — formato a mapear no passo (ver Open questions).
  • OpenCode: opencode.db (SQLite, aberto ?mode=ro), tabelas de session/message/part.
  • Varredura rápida: só metadados na listagem; transcript completo só para as escolhidas. Paralelo com rayon.
  • Fixtures reais anonimizadas por provider em tests/fixtures/.

3. Guarda de compatibilidade (fail-closed, sem amarrar versão)

  • Não travamos por versão do T3 — o nightly sai várias vezes ao dia. A guarda olha só o que importa: as tabelas que vamos tocar e os dados que já estão nelas.
  • Estrutura: SQL completo em sqlite_master (colunas, tipos, NOT NULL, defaults, PK/UNIQUE, índices, triggers) das 8 tabelas, normalizado e comparado com o conjunto aceito em known_schemas.toml; mais schema_version da projeção (hoje 2). Migrations que não mexem nessas tabelas não importam.
  • Formato dos dados (pega o que a DDL não pega): lê uma amostra recente e grande de linhas existentes de cada tabela (payload de thread, mensagem, turn item user_message/assistant_message, provider-thread, metadata_json de eventos, resumeCursor) e valida contra os modelos do t3-import em modo estrito: chave desconhecida, chave obrigatória ausente ou tipo diferente → trava. Assim, se o T3 adicionar um campo ao payload de thread, a gente percebe pela primeira thread nova que ele gravar.
  • Banco vazio (sem amostras) → só a checagem estrutural vale, e o app avisa isso.
  • Pós-escrita: dentro da mesma transação, relê o que gravou e passa pelo mesmo validador antes do commit.
  • Divergência → aborta sem tocar em nada, mostra o diff (tabela/coluna ou campo de payload) e um link github.com/<repo>/issues/new?… pré-preenchido com versão do T3, diff e fingerprint (sem conteúdo de threads).

3b. Janela de manutenção (T3 fechado de verdade)

  • Resolver um T3CODE_HOME canônico e usá-lo em tudo (inclusive na CLI t3, via --base-dir).
  • Antes de cada etapa: server-runtime.json daquele home sem processo vivo; detectar o serviço em background (t3 service) e o app desktop, e pedir para parar (auto-restart incluso). Explicar que lock do SQLite só serializa escrita, não garante que o T3 está fechado.
  • Escrita das threads numa única transação BEGIN IMMEDIATE: revalida guarda e runtime dentro dela, escreve tudo, commit. Nada de lock liberado entre threads.

4. Writer

  • Ordem: guarda → backup (SQLite online backup → statev2.sqlite.bak-t3import-<timestamp>) → criação de projetos → revalidar a guarda → transação das threads. Dry-run nunca cria projeto nem escreve.
  • Projetos: t3 project add <cwd> --base-dir <home> usando a CLI do mesmo build do T3 (o wrapper do app), fora da transação Rust. A CLI offline roda migrations, por isso o backup vem antes e a revalidação depois.
  • Escrita (8 tabelas, nenhuma outra): orchestration_events, orchestration_v2_projection_{threads,messages,turn_items,provider_threads}, orchestration_v2_turn_item_positions, provider_session_runtime, orchestration_v2_projection_metadata. Sem command receipts, outbox, runs, nodes ou bindings de sessão (o nativo também não grava). Nunca as tabelas legadas projection_*.
  • Encoding de evento (espelha OrchestrationEventStore.ts:437): application_event_version=2, aggregate_kind='thread', stream_version começando em 0 por stream, actor_kind='server' (inclusive mensagens de usuário), command_id/causation/correlation = NULL, payload_json só com o payload codificado, envelope (driver, provider instance) em metadata_json. sequence alocado pelo AUTOINCREMENT; last_sequence = sequence do último evento de thread v2 commitado.
  • Ordinais: replicar a normalização do EventSink.ts:309 (itens sem run ficam abaixo de 1_000_000, TurnItemPositionStore.ts:58). Thread que passe desse limite → erro explícito, nunca truncar em silêncio.
  • Ids: app thread import:<instance>:<sessionId>; provider-thread id qualificado por instância (IdAllocator.ts:216). Se o provider-thread id já pertence a outra thread → recusa.
  • Runtime: provider_session_runtime com resumeCursor como o nativo; providerSessionId = null (é a sessão de runtime do T3, não a conversa nativa). Para Claude/Codex, gravar também importedTranscripts como o recordImportedTranscript nativo (o scanner nativo deduplica por isso). Grok/OpenCode não cabem nesse schema → proveniência num manifesto próprio do t3-import, fora do banco do T3.
  • Reimportação: v1 pula thread que já existe. “Atualizar com mensagens novas” vai para a fase 2 e exige manifesto com id estável e hash de cada mensagem de origem, prefixo verificado idêntico, ids de evento novos e timestamps da thread atualizados de forma coerente (ProjectionStore.ts:2634).
  • Teto de mensagens configurável na UI; padrão todas.

5. Oráculo de compatibilidade (dev/CI)

  • Harness TypeScript em oracle/ rodando contra um checkout do t3code (main/nightly).
  • Referência: o mesmo transcript normalizado é escrito pelo caminho real do T3 (EventSink.write + bookkeeping de runtime/importedTranscripts) num banco migrado. Candidato: o Rust escreve no mesmo estado inicial. Compara as 8 tabelas coluna a coluna (JSON canônico).
  • Lê os eventos gravados pelo Rust de volta via OrchestrationEventStore (decode completo contra os contracts) e verifica que as projeções são o que apply produziria.
  • Cenários: banco vazio, banco populado, import repetido, thread grande, colisão de provider-thread id. ProjectionMaintenance.verify como checagem extra (não substitui o diff).
  • O oráculo não é um portão de runtime: é aviso antecipado. Job agendado contra o main/nightly roda o diff; se passar e a DDL ou o formato de payload mudou, gera a atualização de known_schemas.toml e dos modelos para revisão; se falhar, abre issue no repo do t3-import.

6. TUI

  • Lista agrupada por pasta (projeto), com provider, título, data, nº de mensagens, e um marcador “já no T3”.
  • Filtros: provider, busca por texto, intervalo de datas; seleção múltipla por item e por grupo.
  • Painel de opções: teto de mensagens (padrão: todas), dry-run.
  • Tela de confirmação: projetos que serão criados, threads, backup; depois progresso e resumo.

7. Distribuição

  • cargo-dist → GitHub Releases com binários para as 5 targets + instalador shell/PowerShell.
  • README com o aviso: feche o T3 antes; o app faz backup; se travar por schema, abra issue.

Verification

  • Testes unitários dos scanners com fixtures de cada provider.
  • Oráculo: eventos do Rust → projeção real do T3 → diff vazio; verify = valid.
  • Ponta a ponta numa cópia do statev2.sqlite real: importar uma thread de cada provider, abrir o T3 apontando para a cópia (--base-dir), ver a thread no sidebar com histórico completo, mandar uma mensagem e confirmar que o nativeThreadRef.nativeId continua o mesmo depois do primeiro turno (o T3 pode, em falha de resume, abrir sessão nova e fazer handoff do histórico — ProviderTurnStartService.ts:694 — então “respondeu” não prova nada). Um provider por vez: Claude, Codex, Grok (ACP load/resume depende de capability), OpenCode 1 e 2 (session.get).
  • Rodar duas vezes: a segunda não duplica nada.
  • Banco com uma coluna/índice alterado, e banco com um payload de thread contendo um campo desconhecido: em ambos o app trava com a mensagem de issue e não escreve nada.
  • T3 aberto ou serviço ativo durante o import: app recusa antes de criar projeto.

Risks & open questions

  • Risk — deriva de schema: o Nightly muda quase todo dia. Mitigação: guarda fail-closed (estrutura das tabelas + formato dos dados existentes) + oráculo no CI; esperar travas frequentes e um fluxo rápido para validar e liberar cada nightly novo.
  • Risk — projeção divergente silenciosa: uma coluna derivada ou um efeito colateral do apply que não replicamos. Mitigação: o oráculo compara todas as linhas de todas as tabelas, não só as que achamos que mudam.
  • Risk — corromper o banco do usuário: backup obrigatório antes, transação por thread, nunca com T3 aberto.
  • Risk — threads gigantes: um ano de histórico = dezenas de milhares de eventos. É o que o T3 faria nativamente; o teto configurável existe para quem quiser.
  • Open — tool calls: v1 importa texto de usuário e assistente (igual ao nativo). Importar tool calls como turn items (command_execution, file_change…) dá um histórico mais fiel, mas multiplica o mapeamento por provider. Proposta: fase 2, atrás de uma opção.
  • Open — formato do Grok: mapear a estrutura de ~/.grok/sessions e confirmar que o id da sessão é o mesmo que o ACP session/load aceita.
  • Open — providerInstanceId: usar a instância padrão de cada driver nas settings do T3 (settings.json); se o usuário tiver várias, perguntar na UI.
  • Decisão — sessões de worktree: o cwd de execução no v2 vem de thread.worktreePath ou da raiz do projeto (RuntimePolicy.ts:106), e o OpenCode 2 move a sessão se o cwd divergir. Então: se o cwd é um git worktree de um repo que já é (ou vai virar) projeto, a thread vai para esse projeto com worktreePath = cwd original e branch = branch atual do worktree. Se o worktree não existe mais, a thread é importada como só-leitura de fato (histórico) e a UI avisa que retomar vai rodar na raiz do repo.
  • Limite real: “histórico completo” = texto completo; mensagens importadas não têm checkpoints nem fork por run (MessagesTimeline.tsx:2812), igual ao import nativo.
